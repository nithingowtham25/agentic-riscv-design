# Task 4: Ablation Experiment

## 4.1 Objective

The objective of this experiment is to measure the individual effects of **retrieval-augmented generation (RAG)** and **iterative tool feedback** on RTL generation and repair. The experiment was performed under controlled conditions using the same `datapath` module, TAMU provider, and `gpt-5.4` model for all runs.

The experiment consisted of two parts:

- **Part A:** Comparison of `baseline`, `rag`, and `rag_feedback` for unseeded RTL generation.
- **Part B:** Comparison of `rag` and `rag_feedback` when repairing a known-broken `datapath` implementation.

Each configuration was executed three times, resulting in **15 total runs**:

- Part A: 3 arms × 3 runs = **9 runs**
- Part B: 2 arms × 3 runs = **6 runs**

For each unseeded run, `rtl/datapath.sv` was removed before execution to prevent one arm from reusing RTL generated by another arm.

---

The following configurations were used throughout the experiment.

| Parameter | Configuration |
|---|---|
| Target module | `datapath` |
| Provider | TAMU |

| Part A arms | `baseline`, `rag`, `rag_feedback` |

Iteration numbering follows the agent convention where **iteration 0 represents the initial RTL generation/evaluation**. Therefore, a successful run at iteration 0 requires no repair iterations.

### 4.3.3 Baseline Failure Analysis

All three baseline runs produced the same fundamental integration problem. The generated `datapath.sv` instantiated `memory_access` using port names that did not exist in the required `memory_access` interface. The compilation errors included connections such as:

- `funct3`
- `addr`
- `write_data_in`
- `read_data_in`
- `write_data_out`
- `byte_enable`
- `load_data_out`

The required interface instead uses ports such as `MemRW`, `Funct3`, `AddrLSB`, `StoreData`, `ReadData`, `WriteData`, `ByteEnable`, and `LoadData`.

This is a significant integration-level failure because the datapath depends on the exact interfaces of several previously generated modules. Without retrieval, the model repeatedly generated an incompatible interface for `memory_access`.

The fact that the same failure occurred across all three baseline runs also indicates **low run-to-run variation for the baseline**, but consistently incorrect behavior.

### 4.3.4 RAG Behavior

All three RAG runs passed at iteration 0. The retrieval results included project-specific information from sources such as:

- `module_interfaces.md`
- `datapath_integration.md`
- `memory_addressing.md`
- `register_x0_hardwired.md`

In particular, the retrieved `module_interfaces.md` explicitly described the required `memory_access` ports and highlighted incorrect port naming as a common integration failure. This information directly addresses the type of compilation error observed in the baseline runs.

Thus, the Part A results provide evidence that retrieval substantially improved the initial generation of the integrated datapath.

### 4.3.5 Effect of Iterative Feedback in Part A

The `rag_feedback` arm also achieved a 100% pass rate, with all three runs passing at iteration 0.

Therefore, there was no opportunity for the iterative feedback mechanism to demonstrate an additional repair benefit in this experiment. The RAG-generated datapath was already correct before tool feedback was required.

The controlled comparison can therefore be summarized as:

```text
Baseline       → 0/3 passed
RAG            → 3/3 passed
RAG + Feedback → 3/3 passed
```

The improvement from baseline to RAG is measurable in pass rate, while the difference between RAG and RAG+feedback is not observable for this particular unseeded task because both generated correct RTL on the first attempt.

# 4.6 Overall Ablation Analysis

The combined results demonstrate different roles for retrieval and iterative feedback.

### Retrieval effect

For unseeded generation, adding retrieval changed the observed pass rate from:

\[
0\% \rightarrow 100\%
\]

The baseline repeatedly encountered a module-interface integration error, while the RAG configuration retrieved project-specific interface and datapath integration information and produced passing RTL on the first attempt.

This indicates that retrieval was particularly useful for providing **project-specific architectural and interface constraints** that were not reliably reproduced by the baseline generation.

### Iterative feedback effect

The seeded experiment isolates the value of iterative feedback more directly. RAG alone achieved:

\[
0/3 = 0\%
\]

whereas RAG+feedback achieved:

\[
3/3 = 100\%
\]

with exactly one repair iteration for every successful run.

Thus, in the seeded repair experiment, the feedback loop transformed an initially failing RTL implementation into a passing implementation consistently across all three trials.

### Run-to-run variation

The experiment exhibited very little run-to-run variation:

- All three baseline runs failed in the same manner.
- All three RAG Part A runs passed at iteration 0.
- All three RAG+feedback Part A runs passed at iteration 0.
- All three RAG Part B runs failed at iteration 0.
- All three RAG+feedback Part B runs passed after exactly one repair.

This consistency makes the observed differences particularly clear within the three-run sample.
